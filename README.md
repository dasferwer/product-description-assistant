# Помощник для подготовки товарных описаний

Локальный прототип на Python и FastAPI: принимает факты о контрольно-измерительном приборе и через OpenAI API готовит русский черновик карточки для B2B-магазина. Интерфейс — JSON API и Swagger UI. Базы данных и отдельного фронтенда нет.

**Статус проверки:** автоматические тесты используют моки API. Реальные запросы не выполнены: API-ключ и полные исходные данные двух товаров не предоставлены. Примеры результатов этих товаров отсутствуют. Файл `tests/fixtures/synthetic_product.json` содержит искусственные данные только для проверки, это не пример сдачи.

## Установка и запуск

Требуется Python 3.11. Команды выполняются из корня репозитория:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

В `.env` задайте свой `OPENAI_API_KEY` и `OPENAI_MODEL`. Ключ оставлен пустым в примере; `.env` исключён из Git. Переменные окружения имеют приоритет над `.env`. После изменения настроек перезапустите сервер.

Провайдер — OpenAI, официальный Python SDK, Responses API со Structured Outputs. В `.env.example` указана модель `gpt-5.6-terra`; она должна быть доступна вашему API-проекту. Используется `reasoning.effort=low`, поэтому при замене модели нужны поддержка этого режима, Responses API и Structured Outputs. [Документация модели](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте <http://127.0.0.1:8000/docs>. Метод `POST /generate` принимает JSON, кнопка **Try it out** позволяет отправить запрос и скопировать ответ. Полная схема доступна по `/openapi.json`. Без настроек провайдера документация работает, а генерация возвращает `503`.

Сервер предназначен для локального использования и привязан к `127.0.0.1`. Исходные данные отправляются в OpenAI. Приложение не сохраняет товары и не пишет их содержимое или API-ключ в логи. Запросы отправляются с `store=false`.

## Запрос

Все четыре поля обязательны:

| Поле | Тип | Содержание |
| --- | --- | --- |
| `name` | string | Название товара, до 200 символов |
| `manufacturer` | string | Производитель, до 200 символов |
| `specs` | object | До 50 характеристик: ключ до 120 символов, значение — string, number, boolean или null |
| `description` | string | Описание или фрагмент паспорта, до 20 000 символов |

Строковое значение характеристики ограничено 1000 символами. Для точной записи диапазонов, единиц и десятичных запятых используйте строки. Вложенные объекты, массивы, нечисловые значения NaN/Infinity и неизвестные поля отклоняются. Пустой `specs` допустим: факты могут содержаться в паспорте. Универсального списка обязательных характеристик для всех приборов нет.

Пример запроса на искусственных тестовых данных, после настройки ключа:

```bash
curl --fail-with-body --max-time 160 \
  http://127.0.0.1:8000/generate \
  -H 'Content-Type: application/json' \
  --data-binary @tests/fixtures/synthetic_product.json
```

Для своего товара сохраните JSON с указанными четырьмя полями в файл и замените путь после `@`. Сервис не читает локальные файлы сам: `curl` передаёт их содержимое.

## Ответ

`200` возвращается для двух явно различающихся состояний:

| Поле | `status: ready` | `status: needs_clarification` |
| --- | --- | --- |
| `seo_title` | Строка длиной 1–70 символов | null |
| `seo_description` | Связный текст длиной 800–1200 символов | null |
| `key_characteristics` | Массив `{name, value, status}` | Подтверждённые значения и пометки о пропусках/противоречиях |
| `search_queries` | 3–5 разных строк | Пустой массив |
| `commercial` | `{audience: string, tasks: string}` | null |
| `missing_data` | Массив `{field, message, question, blocking}` | Причины и вопросы для уточнения |
| `conflicts` | Пустой массив | Массив `{field, question, sources: [{field, quote}]}` |
| `lengths` | `{seo_title: integer, seo_description: integer}` | null |

`ready` означает черновик, прошедший проверки сервиса, и требует редакторской проверки перед публикацией. `needs_clarification` не является готовой карточкой. При этом состоянии сервис не выдаёт сокращённое описание за описание нужной длины.

Длина считается функцией Python `len()` по итоговой строке: **включая пробелы, знаки препинания и переводы строк**, без подсчёта байтов или токенов. Фрагменты SEO-описания соединяются одним пробелом; учитывается именно полученная строка. Текст не обрезается и не дополняется шаблонным наполнением.

`key_characteristics[].status`: `provided`, `missing` или `conflicting`. Значения из `specs` копируются напрямую с сохранением JSON-типа. Производитель берётся из `manufacturer`. Дополнительные характеристики паспорта допускаются только с дословным подтверждением и проверкой смысла. Для неизвестного или спорного значения выводится `данных нет`. `null`, пустая строка, `данных нет`, `нет данных`, `не указано`, `n/a` и `-` рассматриваются как неизвестное значение.

Пустое название, производитель или описание дают `needs_clarification` с вопросами без вызова модели. Отсутствующий ключ входного JSON — ошибка схемы `422`. Необязательные пропуски могут оставаться в `missing_data` у черновика с `ready`; блокирующий вопрос или противоречие всегда исключает готовую карточку.

## Промпты и проверка достоверности

Рабочие промпты находятся в [app/prompts.py](app/prompts.py), JSON-схемы — в [app/models.py](app/models.py).

1. Генератор получает системные правила и отдельное пользовательское JSON-сообщение с товаром. Инструкции внутри любых полей считаются данными. Разрешены только исходные факты; запрещены догадки о сертификатах, совместимости, гарантии, преимуществах, ценах и других свойствах. Для каждого текстового блока модель указывает поле-источник и дословную цитату.
2. Приложение проверяет схему, типы, обязательные блоки, длины, число и уникальность запросов, существование исходных цитат, числа и распространённые единицы измерения вместе со значениями. Для характеристик из описания проверяется дословное вхождение значения в источник. Характеристики из `specs` модель не переписывает.
3. Второй запрос той же модели с отдельным системным промптом проверяет все блоки по исходному JSON. Он ищет неподтверждённые утверждения, неверную связь значений со свойствами, выдуманную аудиторию, исполнение команд из данных, повторы, пропуски и противоречия. Цитата сама по себе не считается доказательством смысла утверждения.
4. При нарушении формата, длины или достоверности допускается одна новая генерация с замечанием проверки. После второго нарушения возвращается `502 invalid_llm_output`. При подтверждённой нехватке фактов или противоречиях возвращаются вопросы и `needs_clarification` без карточки.

Успешный проход обычно требует двух LLM-вызовов, с исправлением — не более четырёх, без учёта ограниченных сетевых повторов. Полный предыдущий ответ не включается в системные инструкции. Внешние источники, поиск и инструменты модели не используются.

## Ошибки и повторы

Формат ошибки: `{"error": {"code": "…", "message": "…"}}`. У `invalid_input` дополнительно есть `details` с путём и типом ошибки без исходного тела запроса.

| HTTP | Код | Причина |
| --- | --- | --- |
| 422 | `invalid_input` | Повреждённый JSON, неверные типы, пропущенные поля или превышение входных ограничений |
| 503 | `provider_not_configured` | Не заданы ключ или модель |
| 502 | `provider_authorization` | OpenAI отклонил ключ или доступ |
| 503 | `provider_rate_limit` | Лимит запросов или недоступная квота |
| 502 | `provider_error` | Ошибка соединения, провайдера, модели или параметров API |
| 502 | `invalid_llm_output` | Пустой, повреждённый, неполный или неподтверждённый ответ после исправления |
| 504 | `provider_timeout`, `request_timeout` | Таймаут отдельного вызова или всего запроса |

Таймаут HTTP SDK — 30 секунд, полный таймаут одной попытки — 35 секунд, всего endpoint — 150 секунд. Автоматические повторы SDK отключены. Сервис делает не более одного сетевого повтора с задержкой 0,5 секунды для ошибок соединения/таймаутов, HTTP 408, 409, временных 429 и 5xx. Авторизация, постоянные 4xx и `insufficient_quota`/`billing_hard_limit_reached` не повторяются. Сетевой повтор генерации может привести к дополнительному списанию у провайдера, если первый ответ был потерян. Ошибка API не заменяется успешной карточкой.

## Проверка

```bash
python -m pytest -q
```

Тесты покрывают готовый ответ, пропуски, неверный JSON и типы, отсутствие конфигурации, форматы и длины, неподтверждённые числа/единицы и словесные свойства, противоречия, команды внутри описания, пустые и повреждённые ответы, ошибки авторизации, лимиты, таймауты и границы повторов. Отдельные тесты используют настоящий SDK с подменённым HTTP-транспортом и проверяют отправляемую схему и разделение системных правил и данных. Все автоматические тесты выполняются без реального API-ключа и без обращения к OpenAI.

Локально проверены установка по этим командам в новом окружении Python 3.11.13, совместимость зависимостей (`python -m pip check`), запуск Uvicorn, ответы `/docs` и `/openapi.json`, ошибки повреждённого JSON и отсутствующей конфигурации. Эти проверки не подтверждают реальный доступ к OpenAI.

## Ограничения и возможные улучшения

- Семантическая проверка вероятностная: генератор и проверяющий используют одну модель и могут ошибиться одинаково. Точное цитирование и проверка числовых фрагментов не доказывают корректность всех утверждений. Неизвестные единицы, отрицания и сложные смысловые противоречия могут быть пропущены. Устойчивость к произвольным prompt injection не гарантируется; моки проверяют защитный поток, а не поведение реальной модели.
- Достоверность исходного паспорта не проверяется. Если сами исходные сведения неверны, сервис не устанавливает истину из внешних источников. Контент-менеджер должен сверить результат с паспортом.
- Бедные данные могут не позволить подготовить содержательные 800 символов. В этом случае нужен ответ на вопросы сервиса. Готовая карточка не создаётся путём повторов или выдуманных свойств.
- Реальная интеграция и два товарных примера ещё требуют API-ключа, полных исходных данных и разрешения на публикацию этих данных. До их получения утверждать выполнение этих проверок нельзя.
- Следующее полезное улучшение — набор проверенных экспертами товарных примеров и враждебных входов для оценки фактической точности и пропущенных противоречий. Больше сервисов для локального MVP не требуется.
