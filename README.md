# Помощник для подготовки товарных описаний

Локальный прототип на Python и FastAPI: принимает факты о контрольно-измерительном приборе и через Ollama API готовит русский черновик карточки для B2B-магазина. Интерфейс — JSON API и Swagger UI. Базы данных и отдельного фронтенда нет.

**Демонстрационные товары:** поскольку в ТЗ нет полного комплекта исходных данных, для примеров выбраны два реальных прибора по официальному руководству Testo: testo 174 T и testo 174 H с USB-C. Это демонстрационный набор, а не товары, предоставленные работодателем. Искусственные данные автоматических тестов находятся отдельно в `tests/fixtures/`.

## Установка и запуск

Требуются Python 3.11 и [Ollama](https://ollama.com/download). Используется одна модель `qwen2.5:7b`. Если она уже есть в `ollama list`, скачивать её повторно не нужно. При отсутствии модели выполните один раз:

```bash
ollama pull qwen2.5:7b
```

Если Ollama ещё не запущена, выполните `ollama serve` в отдельном терминале. Далее команды выполняются из корня репозитория:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

В `.env` уже указаны `OLLAMA_HOST=http://127.0.0.1:11434` и `OLLAMA_MODEL=qwen2.5:7b`. Локальный Ollama API не требует API-ключа или платного аккаунта. `.env` исключён из Git; переменные окружения имеют приоритет над ним. После изменения настроек перезапустите сервер.

Используется одна модель — `qwen2.5:7b`, API Ollama и [официальный Python SDK](https://github.com/ollama/ollama-python). JSON-схема передаётся через `format`, ответ разбирается Pydantic. Параметры генерации: `temperature=0`, контекст 32 768 токенов, максимум 4500 выходных токенов. [Документация Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs).

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте <http://127.0.0.1:8000/docs>. Метод `POST /generate` принимает JSON, кнопка **Try it out** позволяет отправить запрос и скопировать ответ. Полная схема доступна по `/openapi.json`. Без заданной модели документация работает, а генерация возвращает `503`. При недоступной Ollama или незагруженной модели возвращается понятная ошибка API.

Сервер предназначен для локального использования и привязан к `127.0.0.1`. При адресе Ollama из примера генерация выполняется на этом компьютере, исходные данные не отправляются внешнему LLM-провайдеру. Приложение не сохраняет товары и не пишет их содержимое в логи.

## Запрос

Все четыре поля обязательны:

| Поле | Тип | Содержание |
| --- | --- | --- |
| `name` | string | Название товара, до 200 символов |
| `manufacturer` | string | Производитель, до 200 символов |
| `specs` | object | До 50 характеристик: ключ до 120 символов, значение — string, number, boolean или null |
| `description` | string | Описание или фрагмент паспорта, до 20 000 символов |

Строковое значение характеристики ограничено 1000 символами. Для точной записи диапазонов, единиц и десятичных запятых используйте строки. Вложенные объекты, массивы, нечисловые значения NaN/Infinity и неизвестные поля отклоняются. Пустой `specs` допустим: факты могут содержаться в паспорте. Универсального списка обязательных характеристик для всех приборов нет.

Пример запроса на реальном демонстрационном товаре:

```bash
curl --fail-with-body --max-time 490 \
  http://127.0.0.1:8000/generate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/testo-174-t.input.json
```

Для своего товара сохраните JSON с указанными четырьмя полями в файл и замените путь после `@`. Сервис не читает локальные файлы сам: `curl` передаёт их содержимое.

## Ответ

`200` возвращается для двух явно различающихся состояний:

| Поле | `status: ready` | `status: needs_clarification` |
| --- | --- | --- |
| `seo_title` | Строка длиной 1–70 символов | null |
| `seo_description` | Связный текст длиной 800–1200 символов | null |
| `key_characteristics` | Массив `{name, value, status}` | Подтверждённые значения и пометки о пропусках/противоречиях |
| `search_queries` | 3–5 разных строк | Пустой массив |
| `commercial` | `{audience: string, tasks: string}` | null |
| `missing_data` | Массив `{field, message, question, blocking}` | Причины и вопросы для уточнения |
| `conflicts` | Пустой массив | Массив `{field, question, sources: [{field, quote}]}` |
| `lengths` | `{seo_title: integer, seo_description: integer}` | null |

`ready` означает черновик, прошедший проверки сервиса, и требует редакторской проверки перед публикацией. `needs_clarification` не является готовой карточкой. При этом состоянии сервис не выдаёт сокращённое описание за описание нужной длины.

Длина считается функцией Python `len()` по итоговой строке: **включая пробелы, знаки препинания и переводы строк**, без подсчёта байтов или токенов. SEO-описание — одно поле со связным текстом; минимум 800 символов задан также в схеме генерации. Текст не обрезается и не дополняется шаблонным наполнением.

`key_characteristics[].status`: `provided`, `missing` или `conflicting`. Значения из `specs` копируются напрямую с сохранением JSON-типа. Производитель берётся из `manufacturer`. Если все переданные значения `specs` известны, список строится напрямую из них. Если `specs` пуст или содержит неизвестные значения, модель может дополнительно извлечь характеристики из паспорта; проверяются дословные цитаты и смысл. Необходимые неуказанные сведения модель перечисляет в вопросах для уточнения. Известное значение из `specs` не заменяется извлечённым; расхождения требуют уточнения. Цитаты при противоречиях проверяются по исходным полям. Для неизвестного или спорного значения выводится `данных нет`. `null`, пустая строка, `данных нет`, `нет данных`, `не указано`, `n/a` и `-` рассматриваются как неизвестное значение.

Пустое название, производитель или описание дают `needs_clarification` с вопросами без вызова модели. Отсутствующий ключ входного JSON — ошибка схемы `422`. Необязательные пропуски могут оставаться в `missing_data` у черновика с `ready`; блокирующий вопрос или противоречие всегда исключает готовую карточку.

## Промпты и проверка достоверности

Рабочие промпты находятся в [app/prompts.py](app/prompts.py), JSON-схемы — в [app/models.py](app/models.py).

Три поисковых запроса строятся из проверяемого SEO-заголовка: сам заголовок, заголовок с «характеристики» и с «применение». Это разные поисковые намерения без добавления свойств и обещаний. Они включаются в черновик до семантического аудита.

Если исходное описание уже содержит 800–1200 символов, схема генерации разрешает для SEO-описания только этот исходный текст без изменений. Модель может запросить уточнение; отдельный аудит проверяет все утверждения. Такое сохранение текста не применяется к коротким или слишком длинным описаниям: для них модель составляет новый текст по входным фактам.

1. Генератор получает системные правила и отдельное пользовательское JSON-сообщение с проверенными полями товара. Инструкции внутри любых полей считаются данными. Разрешены только исходные факты; запрещены догадки о сертификатах, совместимости, гарантии, преимуществах, ценах и других свойствах. Для генерируемых текстовых блоков модель выбирает идентификаторы полей-источников из ограниченного списка; их значения приложение берёт из исходного JSON напрямую.
2. Приложение проверяет схему, типы, обязательные блоки, длины, число и уникальность запросов, существование полей-источников и непредусмотренное смешение алфавитов в словах. Числа и распространённые единицы вместе со значениями сверяются со всем набором исходных полей; отдельно проверяются явная замена производителя и отдельные формы инверсии отрицаний. Отдельный словарный фильтр отклоняет неподтверждённые обещания, свойства и преимущества, включая гарантии, безопасность, надёжность, совместимость и сертификацию. Для характеристик из описания и противоречий проверяются дословные цитаты. Характеристики из `specs` модель не переписывает.


3. Второй запрос той же модели с отдельным системным промптом проверяет все блоки по исходному JSON. Он ищет неподтверждённые утверждения, неверную связь значений со свойствами, выдуманную аудиторию, исполнение команд из данных, повторы, пропуски и противоречия. Цитата сама по себе не считается доказательством смысла утверждения.
4. При нарушении формата, длины или достоверности допускается одна новая генерация с замечанием проверки. После второго нарушения возвращается `502 invalid_llm_output`. При подтверждённой нехватке фактов или противоречиях возвращаются вопросы и `needs_clarification` без карточки.

В Ollama 0.24.0 большие `maxLength` приводят к ошибке компиляции грамматики. Для API убираются только эти ограничения из копии схемы; полная схема используется при обязательной проверке Pydantic. Правила длины также заданы в системном промпте. Ограничения длины результата не ослабляются. Перед вызовом проверяется консервативный бюджет UTF-8-байтов инструкций и данных с резервом на ответ; слишком большой ввод отклоняется без обрезки.

Успешный проход обычно требует двух LLM-вызовов, с исправлением — не более четырёх, без учёта ограниченных сетевых повторов. Полный предыдущий ответ не включается в системные инструкции. Внешние источники, поиск и инструменты модели не используются.

## Ошибки и повторы

Формат ошибки: `{"error": {"code": "…", "message": "…"}}`. У `invalid_input` дополнительно есть `details` с путём и типом ошибки без исходного тела запроса.

| HTTP | Код | Причина |
| --- | --- | --- |
| 422 | `invalid_input` | Повреждённый JSON, неверные типы, пропущенные поля или превышение входных ограничений |
| 422 | `input_context_limit` | Данные вместе с инструкциями превышают безопасный бюджет контекста |
| 503 | `provider_not_configured` | Не заданы модель или адрес Ollama |
| 502 | `provider_authorization` | LLM-сервер отклонил доступ |
| 503 | `provider_rate_limit` | LLM-сервер вернул ограничение запросов |
| 502 | `provider_error` | Ошибка соединения, провайдера, модели или параметров API |
| 502 | `invalid_llm_output` | Пустой, повреждённый, неполный или неподтверждённый ответ после исправления |
| 504 | `provider_timeout`, `request_timeout` | Таймаут отдельного вызова или всего запроса |

Таймаут HTTP SDK — 110 секунд, полный таймаут одной попытки — 120 секунд, всего endpoint — 480 секунд. Сервис делает не более одного сетевого повтора с задержкой 0,5 секунды для ошибок соединения/таймаутов, HTTP 408, 409, 429 и 5xx. Авторизация и постоянные 4xx не повторяются. Ошибка API не заменяется успешной карточкой.

## Проверка

```bash
python -m pytest -q
```

Тесты покрывают готовый ответ, пропуски, неверный JSON и типы, отсутствие конфигурации, форматы и длины, неподтверждённые числа/единицы и словесные свойства, противоречия, команды внутри описания, пустые и повреждённые ответы, ошибки авторизации, лимиты, таймауты и границы повторов. Отдельные тесты используют настоящий SDK с подменённым HTTP-транспортом и проверяют отправляемую схему и разделение системных правил и данных. Все автоматические тесты выполняются без обращения к реальной модели.

Тестовые данные искусственные и не используются как примеры сдачи. В новом окружении Python 3.11 выполнены установка зафиксированных зависимостей, `pip check`, 72 автоматических теста и запуск Uvicorn. Проверены `/docs`, `/openapi.json`, неверный JSON и пустые данные.

Отдельно выполнены реальные HTTP-запросы к `POST /generate` для обоих демонстрационных товаров через Ollama 0.24.0 и `qwen2.5:7b`. Сохранённые ответы прошли проверку схемы, длин и совпадения характеристик с входом, а также ручную сверку с исходными данными. Длины описаний — 989 и 1022 символа. Это реальные ответы API, а не результаты моков.

## Ограничения и возможные улучшения

- Семантическая проверка вероятностная: генератор и проверяющий используют одну модель и могут ошибиться одинаково. Ссылка на исходное поле, словарный фильтр и проверка числовых фрагментов не доказывают корректность всех утверждений. Фильтр может дать ложный отказ и не охватывает все перефразировки. Неизвестные единицы, отрицания и сложные смысловые противоречия могут быть пропущены. Устойчивость к произвольным prompt injection не гарантируется; моки проверяют защитный поток, а не поведение реальной модели.
- Достоверность исходного паспорта не проверяется. Если сами исходные сведения неверны, сервис не устанавливает истину из внешних источников. Контент-менеджер должен сверить результат с паспортом.
- Бедные данные могут не позволить подготовить содержательные 800 символов. В этом случае нужен ответ на вопросы сервиса. Готовая карточка не создаётся путём повторов или выдуманных свойств.
- В примерах использованы самостоятельно выбранные реальные приборы из официального руководства. Исходный PDF задания не содержит полного набора данных товаров работодателя; пример DM 02 не выдан за такой набор. API-ключ при выбранной локальной модели не нужен.
- Следующее полезное улучшение — набор проверенных экспертами товарных примеров и враждебных входов для оценки фактической точности и пропущенных противоречий. Больше сервисов для локального MVP не требуется.
